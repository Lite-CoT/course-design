## 发现的问题与修改

修复前的新增检查日志保留在`evidence/2026-10-27-challenges/before-fixes.txt`，最终回归日志为同目录`regressions.txt`。测试先复现，再修改程序；没有把一般异常当作“安全拒绝”计为通过。

| 问题 | 修复前实际行为 | 最终处理与验证 |
| --- | --- | --- |
| 数据库索引和回执不在完整审计范围内 | 改动voter_id、nonce列或receipt，状态查询仍返回成功；索引影响防重复和回执查询 | 同一事务中读取四列，先核验签名选票集合，再逐行核对ID、nonce及回执的签名、摘要、轮次与时间；状态查询、写入和重启审计都经过这条路径 |
| TLS握手位于监听线程 | 一个只连接TCP却不发送ClientHello的客户端，使另一个正常客户端在2秒测试窗口内无法查询 | 将握手移入独立工作线程，保留10秒握手超时；回归在坏连接仍保持打开时验证正常查询完成 |
| 汇总票数类型不严格 | Python中True等于1，1票的汇总包改为`accepted:true`仍通过字典相等比较 | 在比较完整汇总前要求`type(accepted) is int`，并校验计时字段为合理非负数值 |
| 文件和网络JSON解析不一致 | 超深数组未被主动限制，超长整数抛出普通ValueError；错误未统一为可解释拒绝 | 共用严格解析函数，限制容器嵌套64层，重复键/非有限常量/解析超限拒绝并转换为VoteError；同时验证异常HTTP请求不增加票数且后续正常投票仍可用 |

修复审计时，首轮回归还暴露了新增循环变量覆盖状态记录的问题，随后已改用独立`state`变量并复跑完整回归。最终日志与证据来自全部修正后的版本。

## 实测性能

Windows本机、Intel Core i7-13700KF（16核/24逻辑处理器）、Python 3.12、Paillier 2048位、3个选项。下面均为3次实际运行均值，单位ms；硬件与文件哈希见证据目录。测试在普通共享工作电脑上执行，没有控制系统背景负载，保留波动，不只选择最快一次。

300票完整投票阶段3次分别为62281.68、62948.14、85531.51ms，均值约70.25秒。逐次精确值以`source/challenges.json`为准，CSV保留未四舍五入数值。完整阶段包括每个客户端连接、获取配置、查询状态和回执、加密、提交及服务器审计；不含初始化、关闭、导出和保管端处理，后几项另有计时字段。

正常投票中的持续完整审计是当前主要开销来源：每次读取都核验已有集合和回执，累计工作约O(N²)。本轮保留完整验证路径，并明确规模限制；没有跳过审计以降低时间。单机TLS数据不代表跨电脑延迟或并发容量。

## 仍然存在的安全局限

两项`limitation_demonstration`均复现了风险：恶意客户端的`[2,0]`和`[0,0]`合计仍满足两票约束；持登记私钥的恶意服务器可在首次送审前重签删票集合。它们不是“攻击已被防御”的通过项。另有单人总票直接暴露其选择、完整私钥持有者可自行解密单票、未实现生产级连接限额等边界。

任务书要求对发现不了的篡改说明局限。这里的实现仍以正确执行协议的无Paillier私钥服务器为隐私边界，未增加独热零知识证明、外部透明日志或门限解密。答辩应分别说明随机密文、签名完整性、选票有效性证明和服务器可信假设，不能互相替代。
